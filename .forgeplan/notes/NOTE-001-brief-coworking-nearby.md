## Цель, аудитория и сценарий

Аудитория — пользователь личного чата Telegram, выбирающий место для работы из подготовленной владельцем подборки; владелец отвечает за наполнение и актуальность каталога. Дополнительные сегменты и количественный спрос исходником не установлены.

Сценарий (§1–3): /start → инструкция с актуальным RESULTS_LIMIT и обычной кнопкой request_location → message.location (допустимо venue.location), в том числе до /start → вводный текст → отдельная карточка каждого результата в порядке расстояния, ответом на исходное сообщение → открытие маршрута. Новая точка означает новый самостоятельный подбор; старые URL сохраняют прежнее начало. /help объясняет источник мест и расстояние по прямой. Группы направляются в личный чат; live location обрабатывается только по исходному сообщению без повторного подбора по edited_message.

## Решения владельца и границы MVP

Приняты (§1, 9, 13, 14): русский интерфейс, только каталог владельца, по умолчанию 3 результата (RESULTS_LIMIT 1–5), Haversine по прямой, оценки и описания только из каталога, без зашитого города и скрытого радиуса. Яндекс рассчитывает маршрут при открытии обычной HTTPS-ссылки; API Яндекса и его ключ базовому поиску не нужны. Постоянная БД, Redis, HTTP-сервер, Mini App и LLM для сценария не нужны. Один процесс/сервис и JSON; обновление каталога с перезапуском.

Вне MVP: интернет-поиск всех мест, сбор отзывов/рейтингов, сортировка по времени, слежение, доступность мест, «открыто сейчас», бронирование, платежи, профили, избранное, админпанель; также не требуются Google Sheets и загрузка каталога через Telegram. Обогащение API — отдельная задача с проверкой интерфейса и условий; HTML-скрейпинг, недокументированные поля и бессрочное сохранение API-ответов без проверки условий не допускаются. Платные ресурсы и публикация требуют отдельного поручения.

## Сохранённые ограничения и детали intake

Каталог (§4): локальный UTF-8 JSON, массив, филиал=запись, default data/coworkings.json. Обязательны уникальный непустой id ≤64, name ≤150, address ≤250 с городом/домом, конечные latitude [-90,90], longitude [-180,180]. Boolean/NaN/∞ не координаты; ноль допустим, совпадающие координаты разных id допустимы. active:boolean default true; yandex_maps_url HTTPS allowlist или null; short_review ≤200; description ≤500; rating_text ≤50; rating_source catalog/yandex default catalog; rating_checked_at и updated_at даты YYYY-MM-DD либо null. Пустые optional строки после trim отсутствуют. rating_text+yandex требуют даты и ссылки. Неизвестные поля, duplicate id, неверные типы и схема отклоняются целиком до polling с полем и id/индексом. Пустой массив валиден, отсутствующий файл — понятная ошибка. Общий валидатор для бота и отдельной команды. Адрес, ссылка и ll не заменяют явные координаты; страница URL в рантайме не загружается.

Алгоритм (§5): проверить origin, отобрать active, Haversine R=6 371 000 м с радианами и clamp [0,1], сортировать точные distance_m до округления, tie-break id ascending, взять min(limit, count). Менее 1 км — метры с ещё не определённым разумным округлением; от 1 км — один десятичный знак км. «Примерно» и «по прямой» обязательны; далёкие места не называются «рядом». Рейтинг не меняет порядок, расстояние не преобразуется во время дороги.

Маршруты (§6): https://yandex.ru/maps/?rtext={user_lat},{user_lon}~{place_lat},{place_lon}&rtt={mode}; pd/mt/auto. Стандартное URL-кодирование, точка в числе, до шести десятичных знаков; latitude до longitude, origin до destination. Обе точки явные, без замены городом/метро/«текущим местоположением» и без browser geolocation. Отдельная ссылка организации не заменяет маршрут. Работает веб-ссылка без приложения; перенаправление зависит от клиента.

Карточки (§3): номер+название → адрес → примерное расстояние → optional rating → short_review → description → три кнопки → optional «Место в Яндекс Картах». Тексты кнопок и порядок сохранены в приложении. catalog подписывается «Оценка из списка», yandex — «Рейтинг Яндекс Карт: … · проверен ДД.ММ.ГГГГ». Без rating нет звёздной строки; без short_review/description — точные fallback исходника. Шкала не конвертируется, характеристики не выдумываются. HTML экранируется; валидная карточка помещается в одно сообщение.

Ошибки/concurrency/privacy (§8–9): точные три сообщения для неподходящего ввода, невалидной точки и пустой подборки сохранены в приложении. 1–2 записи показываются без дублей, дальние/нулевые/отрицательные координаты обрабатываются. Один чат последователен, origin локален каждому запросу; у разных чатов нет общей изменяемой «последней точки». Блокировка бота завершает отправку пользователю без падения процесса. Telegram ошибки контролируются, 429 учитывает retry_after, бесконечных повторов нет; частичную выдачу нельзя целиком автоматически переслать без анализа отправок. Логи без токена, точных координат и полных route URL; допустимы код/этап/обезличенный request id. Геопозиция только в памяти обработки, после неё нет истории поисков/координат приложения; история Telegram этим не удаляется.

1. ЦЕЛЬ И ОСНОВНЫЕ РЕШЕНИЯ

Пользователь отправляет свою геопозицию в личный чат Telegram-бота и получает три ближайших коворкинга из заранее подготовленного владельцем списка. У каждого места есть краткая оценка, описание, расстояние и ссылки на маршрут в Яндекс Картах от присланной точки.

Принятые настройки первой версии:

• Язык интерфейса — русский.
• Источник рекомендованных мест — исключительно каталог владельца.
• Число результатов по умолчанию — 3; меняется настройкой.
• Близость означает расстояние по прямой между координатами.
• Описание и краткая оценка берутся из каталога.
• Яндекс Карты рассчитывают дорожный маршрут после открытия ссылки.
• Под каждой карточкой есть маршруты пешком, на общественном транспорте и на машине.
• Город не зашит в алгоритм: бот работает с географией предоставленного каталога.
• Для обычного подбора бот не обращается к API Яндекса.

Что означает опора на Яндекс Карты в этом MVP: в каталоге находятся заранее проверенные владельцем координаты и ссылки на места; пользователь получает маршрут между своей точкой и точкой выбранного коворкинга в Яндекс Картах.

Автоматическое чтение актуального рейтинга Яндекса и сортировка по времени дороги требуют отдельной интеграции. Они не являются скрытым условием работоспособности базовой версии.


2. ПОЛЬЗОВАТЕЛЬСКИЙ СЦЕНАРИЙ

FR-01. Пользователь может открыть личный чат и отправить /start.

Ответ:
«Отправь геопозицию — покажу 3 ближайших коворкинга из подборки с оценкой, описанием и маршрутами в Яндекс Картах».

Число в тексте должно соответствовать RESULTS_LIMIT.

Под сообщением находится обычная клавиатурная кнопка:
«📍 Отправить геопозицию».

Для кнопки используется KeyboardButton с request_location=true. Эта возможность Telegram предназначена для личных чатов. [1]

FR-02. Пользователь может прислать геопозицию кнопкой или вручную через меню вложений Telegram. Бот принимает message.location; если пользователь отправил карточку места, допускается использовать message.venue.location.

Любая присланная точка считается выбранной точкой отправления. Бот не пытается установить, находится ли человек физически именно там.

FR-03. После получения координат бот выбирает ближайшие активные записи и отправляет:

«Ближайшие коворкинги из подборки. Расстояние указано по прямой; время в пути смотри в Яндекс Картах».

Затем отправляет отдельное сообщение на каждый результат, в порядке увеличения расстояния.

FR-04. Пользователь может сразу отправить другую геопозицию. Бот выполняет новый подбор, пересчитывает расстояния и формирует новые ссылки от новой точки.

Результаты отвечают на соответствующее сообщение с геопозицией. Это позволяет отличить несколько последовательных запросов. Старые ссылки продолжают относиться к исходной точке того запроса, для которого были созданы.

FR-05. Пользователь может отправить /help и получить короткое объяснение: как прислать точку, откуда берутся места и что означает расстояние по прямой.

В групповых чатах бот не выполняет подбор и предлагает открыть личный чат. Фоновое отслеживание перемещений не используется. Для live location обрабатывается исходная точка; последующие edited_message не запускают поток новых подборок.


3. КАРТОЧКА КОВОРКИНГА

Обязательный порядок:

1. Номер результата и название.
2. Полный адрес.
3. Примерное расстояние по прямой.
4. Оценка из списка, если добавлена.
5. Краткий вывод о месте из списка.
6. Описание из списка.
7. Кнопки маршрутов.
8. Кнопка «Место в Яндекс Картах», если в каталоге есть соответствующая ссылка.

Синтетический пример оформления, не сведения о реальном заведении:

1. Демо — коворкинг «Точка»
📍 Москва, тестовый адрес
📏 Примерно 1,2 км по прямой
⭐ Оценка из списка: 8/10
💬 Тихо, удобно работать одному.
Рабочая зона с розетками и отдельной комнатой для звонков.

Кнопки:
«🚶 Пешком» и «🚇 Транспорт»
«🚗 На машине»
«📍 Место в Яндекс Картах» — только если ссылка предоставлена.

Оценка не обязана быть числом: каталог может содержать «8/10», «4,7/5» или текстовую характеристику. Бот не переводит оценки на придуманную шкалу.

Если источник rating_text — catalog, подпись: «Оценка из списка».
Если источник — yandex, подпись: «Рейтинг Яндекс Карт: … · проверен ДД.ММ.ГГГГ». Это сохранённое значение из каталога, не обещание текущего рейтинга.

Если rating_text отсутствует, отдельная строка со звездой не выводится.
Если short_review отсутствует, выводится «Краткая оценка пока не добавлена».
Если description отсутствует, выводится «Описание пока не добавлено».

Не генерировать оценку, достоинства, недостатки или описание с помощью LLM. Не выводить предположения о качестве Wi-Fi, наличии мест, ценах и работе заведения.

Для текстов достаточно обычного Telegram HTML с экранированием содержимого каталога. Названия, амперсанды, кавычки и угловые скобки должны отображаться корректно. Ограничения длины задаются в контракте, поэтому валидная карточка помещается в одно сообщение.


4. КАТАЛОГ КОВОРКИНГОВ

Основной формат: локальный JSON в UTF-8.
Путь по умолчанию: data/coworkings.json.
Верхний уровень — массив объектов.
Одна запись означает один конкретный филиал.
Владелец обновляет файл и перезапускает процесс бота.

Административная панель, Google Sheets и загрузка файла через Telegram для первой версии не требуются. Реальный список будет предоставлен отдельно; его нужно привести к указанному формату без добавления вымышленных мест.

Обязательные поля:

• id: непустая строка до 64 символов, уникальная во всём каталоге.
• name: непустая строка до 150 символов.
• address: непустая строка до 250 символов, с городом и номером дома.
• latitude: конечное число от −90 до 90.
• longitude: конечное число от −180 до 180.

Дополнительные поля:

• active: boolean; по умолчанию true.
• yandex_maps_url: HTTPS-ссылка на место в Яндекс Картах или null.
• short_review: краткая оценка, одна-две фразы до 200 символов, либо null.
• description: описание до 500 символов, либо null.
• rating_text: текст оценки до 50 символов, либо null.
• rating_source: catalog или yandex; по умолчанию catalog.
• rating_checked_at: дата YYYY-MM-DD или null.
• updated_at: дата последней правки записи YYYY-MM-DD или null.

Если rating_text заполнено и rating_source=yandex, требуются rating_checked_at и yandex_maps_url. Если происхождение оценки не установлено, её нельзя подписывать как рейтинг Яндекса.

Пустые дополнительные строки после удаления внешних пробелов считаются отсутствующими. Для числовых координат запрещены boolean, NaN и бесконечность. Ноль — допустимое значение. Две разные записи могут иметь одинаковые координаты.

yandex_maps_url проверяется как HTTPS URL с доменом Яндекс Карт из явного списка разрешённых доменов. Относительные ссылки, javascript: и произвольные сторонние URL отклоняются. В рантайме бот не загружает эту страницу.

Координаты хранятся отдельными именованными полями. Нельзя считать параметр ll произвольной ссылки координатами заведения: это может быть центр отображаемой карты. Одна короткая ссылка или один адрес не заменяют явные latitude и longitude.

Пример записи — только для документации и тестового каталога:

{
  "id": "demo-001",
  "name": "ДЕМО — Тестовый коворкинг",
  "address": "Москва, тестовый адрес",
  "latitude": 55.750000,
  "longitude": 37.610000,
  "active": true,
  "yandex_maps_url": null,
  "short_review": "Тихо, удобно работать одному.",
  "description": "Синтетическое описание для проверки карточки.",
  "rating_text": "8/10",
  "rating_source": "catalog",
  "rating_checked_at": null,
  "updated_at": "2026-10-18"
}

Пример не утверждает, что по этим координатам существует коворкинг.

Загрузка и валидация:

• Каталог читается и целиком проверяется при запуске.
• Невалидный JSON, повторные id и ошибки схемы приводят к понятной диагностике с id или индексом записи и названием поля.
• Бот не запускается с частично и незаметно испорченным каталогом.
• Пустой массив допустим: бот запускается и сообщает, что подборка пока пуста.
• Отсутствующий файл — ошибка конфигурации с понятной инструкцией.
• Неизвестные поля отклоняются с объяснением, чтобы опечатки не терялись.
• Один и тот же валидатор используется ботом и отдельной командой проверки каталога.


5. АЛГОРИТМ ПОДБОРА

FR-06. Пользователь может получить ближайшие места исключительно из активных записей каталога.

Порядок действий:

1. Проверить входные latitude и longitude.
2. Выбрать все записи с active=true.
3. Рассчитать географическое расстояние до каждой записи по Haversine.
4. Отсортировать по точному расстоянию до округления.
5. При точном равенстве расстояний использовать id по возрастанию для стабильного результата.
6. Взять min(RESULTS_LIMIT, число активных записей).
7. Сформировать карточки и ссылки.

Для Haversine использовать сферическую модель Земли, радиус 6 371 000 м и углы в радианах. Промежуточное значение перед извлечением обратной тригонометрической функции ограничивать диапазоном [0, 1] для защиты от погрешности вычислений.

Внутри приложения расстояние хранится в метрах. Для интерфейса:

• меньше 1 км — метры с разумным округлением;
• от 1 км — километры с одним десятичным знаком;
• обязательно указать «примерно» и «по прямой».

Не задавать скрытый радиус, который исключит все результаты. Если все места далеко, показать реальные расстояния и формулировку «ближайшие из подборки». Не называть далёкие места находящимися «рядом».

Оценка не меняет порядок выдачи: задача пользователя — найти ближайшие варианты. Нельзя поднимать более далёкий коворкинг из-за более высокого балла.

Не пересчитывать расстояние по прямой во время пешей прогулки. Мосты, заборы, дороги, транспорт и пробки учитываются только при расчёте маршрута самим Яндексом.


6. МАРШРУТНЫЕ ССЫЛКИ

FR-07. Пользователь может открыть маршрут от присланной точки до каждого результата.

Шаблон: [2]

https://yandex.ru/maps/?rtext={user_lat},{user_lon}~{place_lat},{place_lon}&rtt={mode}

Порядок в rtext — широта, долгота. Первой идёт точка пользователя, второй — коворкинг. Тип маршрута задаётся явно:

• pd — пешком;
• mt — общественный транспорт;
• auto — на машине.

Использовать обычные HTTPS URL. Собрать параметры стандартным URL-кодировщиком, без локализованных десятичных запятых. Числа — с точкой, до шести знаков после неё.

Кнопки должны вести сразу на маршрут с обеими точками. Нельзя подставлять город, метро или «текущее местоположение» вместо полученных координат. Боту не нужно получать доступ к геолокации браузера.

Яндекс Карты рассчитывают маршрут при открытии ссылки. Веб-вариант должен работать и без установленного приложения; конкретное перенаправление в приложение зависит от клиента.

Ссылка на карточку организации хранится отдельно и не заменяет маршрутную ссылку.


7. ИСТОЧНИКИ ДАННЫХ И ГРАНИЦЫ ИНТЕГРАЦИИ

FR-08. Пользователь получает описание и краткую оценку именно из исходного каталога.

В проверенном публичном HTTP API Поиска по организациям Яндекса рейтинг, число оценок и тексты отзывов не входят в документированный гарантированный контракт. Поле description там является подзаголовком результата и не заменяет пользовательское описание коворкинга. [3]

Для MVP:

• Каталог предоставляет владелец.
• Название, филиал, адрес, координаты и ссылка должны соответствовать одному месту.
• Оценки из Яндекса, если они уже есть в списке, отображаются с источником и датой проверки.
• При отсутствии данных используются правила пустых полей из раздела 3.
• Обычный поиск не зависит от доступности Яндекс API.

Возможное последующее обогащение через Геокодер или Поиск организаций оформляется отдельной задачей после проверки доступных полей и условий выбранного доступа. Не делать HTML-скрейпинг, не использовать недокументированные поля и не планировать бессрочное сохранение API-ответов без проверки применимых условий.


8. ОШИБКИ И НЕСТАНДАРТНЫЕ СИТУАЦИИ

• Текст, фото или стикер вместо точки: «Пришли геопозицию через кнопку ниже или через меню вложений Telegram».
• Некорректные координаты: «Не получилось прочитать геопозицию. Отправь её ещё раз».
• Нет активных мест: «В подборке пока нет коворкингов».
• В каталоге одно или два активных места: показать их все, без дублирования.
• Пользователь за пределами города: выполнить обычный поиск по каталогу и честно показать расстояние.
• Координаты совпали с коворкингом: корректно обработать нулевое расстояние.
• Новая геопозиция во время обработки предыдущей: запросы одного чата обрабатываются последовательно; координаты каждого запроса остаются локальными.
• Несколько пользователей одновременно: никакого общего изменяемого состояния с последней геопозицией.
• Пользователь заблокировал бота: завершить отправку ему без падения процесса.
• Временная ошибка Telegram: контролируемая обработка; при 429 учитывать retry_after, не выполнять бесконечные повторы.
• При частично отправленной выдаче не переотправлять весь набор автоматически без разбора результата предыдущих отправок.

Точные координаты, токен и полные URL маршрутов не должны попадать в логи. Ошибки можно фиксировать кодом, этапом обработки и обезличенным идентификатором запроса.


9. ТЕХНИЧЕСКОЕ РЕШЕНИЕ

Рекомендуемый стек для нового проекта:

• Python 3.12.
• aiogram 3.x для Telegram Bot API. [4]
• Стандартный JSON как каталог.
• pytest для проверок алгоритма и обработчиков.
• Обычный запуск через long polling.
• Dockerfile и простой compose.yaml для запуска одним сервисом.

При существующем репозитории использовать совместимые решения проекта. Конкретные версии зависимостей зафиксировать после проверки совместимости; не использовать плавающий latest в сборке.

Достаточно одного приложения и файла каталога. Постоянная база данных, Redis, отдельный HTTP-сервер, Mini App и LLM не нужны для указанного сценария.

Разделить ответственность:

• конфигурация и запуск;
• загрузка и валидация каталога;
• расчёт расстояний и сортировка;
• сборка ссылок;
• форматирование карточек;
• обработчики Telegram.

Предлагаемые внутренние контракты:

load_catalog(path) -> list[Coworking]
find_nearest(origin, coworkings, limit) -> list[SearchResult]
build_yandex_route_url(origin, destination, mode) -> str
render_card(search_result, position) -> text_and_keyboard

Coworking хранит поля каталога.
SearchResult хранит ссылку на Coworking и distance_m.
Origin содержит latitude и longitude конкретного запроса.
Контракты можно адаптировать к стилю существующего проекта без изменения поведения.

Конфигурация:

BOT_TOKEN — обязательный секрет Telegram.
CATALOG_PATH — по умолчанию data/coworkings.json.
RESULTS_LIMIT — по умолчанию 3; целое от 1 до 5.
LOG_LEVEL — по умолчанию INFO.

Ключ Яндекса не требуется конфигурации базового варианта, поскольку бот лишь создаёт обычные ссылки.

Геопозиция используется в памяти в пределах обработки запроса. После отправки результатов приложение не хранит координаты или историю поисков. Это не означает удаления сообщений и маршрутных ссылок из истории Telegram.


10. ПРОВЕРКИ И КРИТЕРИИ ПРИЁМКИ

AC-01. /start в личном чате выдаёт инструкцию и кнопку передачи геопозиции.

AC-02. Геопозиция, отправленная вручную до /start, тоже обрабатывается.

AC-03. На синтетическом каталоге с заранее известным порядком расстояний бот выбирает правильные три активные записи, независимо от их порядка в файле.

AC-04. Для двух специально подобранных тестовых точек с разным ожидаемым порядком результаты соответствуют ожидаемому порядку. Координаты начала во всех новых ссылках соответствуют новой точке. Небольшое перемещение пользователя не обязано менять порядок мест.

AC-05. В выдаче нет записей вне каталога; active=false исключается.

AC-06. Сортировка выполняется до округления. При равных расстояниях порядок стабилен. Совпадающие координаты разных записей допустимы.

AC-07. Для каждой из трёх кнопок проверяются HTTPS-домен, обе пары координат, порядок latitude/longitude и соответствующий rtt. URL проверяется через разбор query-параметров, а не только сравнением строк.

AC-08. Отдельный регрессионный тест выявляет перестановку широты и долготы. Для примера Москвы широта около 55, долгота около 37 должны попадать в соответствующие позиции.

AC-09. В карточке явно написано «по прямой». Она не содержит вычисленного ботом времени дороги или километров маршрута.

AC-10. Оценка, краткий вывод и описание совпадают с каталогом; отсутствующие значения не превращаются в нулевой рейтинг или выдуманные характеристики.

AC-11. Оценка с rating_source=catalog не подписывается как рейтинг Яндекса. При заполненном rating_text и rating_source=yandex отсутствие даты проверки или ссылки вызывает понятную ошибку валидации.

AC-12. Проверены пустой каталог, одна запись, две записи и отсутствие активных записей.

AC-13. Проверены нулевые координаты, совпадение точек, отрицательные координаты и далёкая точка пользователя.

AC-14. Невалидный JSON, отсутствующий файл, повторный id, неверные типы и координаты вне диапазона диагностируются до запуска polling.

AC-15. Тексты с символами &, <, > и кавычками отправляются без повреждения разметки.

AC-16. Параллельные запросы двух пользователей не смешивают точки отправления, адресатов и карточки.

AC-17. Ошибки Telegram и блокировка бота одним пользователем не останавливают приложение.

AC-18. Логи не содержат BOT_TOKEN, точных координат пользователя или URL с его координатами.

Основные автоматические проверки работают без реальных ключей и живых запросов к Telegram или Яндексу: внешнюю отправку заменить тестовым адаптером.

После предоставления токена и реальных записей провести ручную проверку: отправить две геопозиции и открыть все три типа маршрута для одного результата. Проверить старт, финиш и режим. Если устройство или сервис недоступны, отметить эту проверку как невыполненную, не заявлять её прохождение.

Задача 3. Подбор и маршруты.

Задача 5. Проверки и подготовка запуска.

13. ВНЕ ПЕРВОЙ ВЕРСИИ

Поиск всех коворкингов в интернете; автоматическое извлечение отзывов и рейтингов; сортировка по времени маршрута; постоянное слежение; проверка свободных мест и «открыто сейчас»; бронирование; платежи; профили; избранное; административная панель.

Если потребуется выбирать места по реальному времени дороги, это отдельное изменение: необходим источник маршрутных длительностей для кандидатов и выбранного транспорта. Сортировка по прямой не должна переименовываться в сортировку по времени.


14. ВХОДНЫЕ ДАННЫЕ ДЛЯ РЕАЛЬНОГО ЗАПУСКА

Владелец предоставляет список коворкингов и Telegram BOT_TOKEN.

Для каждой записи нужны название, полный адрес и координаты; для полноценной карточки — краткая оценка, описание и ссылка на Яндекс Карты. Если в исходном списке есть только адреса или ссылки, подготовка и проверка координат — отдельный этап наполнения каталога. Не обещать автоматическое извлечение координат из любой ссылки.

Пока эти данные не предоставлены, подготовить рабочую реализацию на изолированных синтетических тестах и оставить настоящий каталог пустым.
